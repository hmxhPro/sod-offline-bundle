## 1. 一句话定位

SOD（Small Object Detection / 视频检测控制台）是一套**可离线部署的开放词汇目标检测系统**：用户用自然语言描述要找的目标，系统对视频或图片做检测与跨帧跟踪，并在网页端完成标注、训练自定义模型、以及大模型辅助标注。

当前仓库是 **Windows 便携离线包**（`sod-offline-bundle`）。应用本体是 `backend` + `frontend`；Node.js、Miniconda（含 CUDA 版 PyTorch）、便携 PostgreSQL 全部装在 `windows\runtime\` 下，不写系统 PATH、不建 Windows 服务。

**技术主轴**：FastAPI + YOLOE（开放词表）+ ByteTrack + React。自定义训练实际微调的是 **Ultralytics YOLOv11 检测模型**，不是 YOLOE 本身；开放词汇检测仍走 YOLOE。

## 2. 运行时拓扑

日常生产模式是三个用户态进程 + 一个便携数据库：

```
浏览器
  │  http://localhost:8080/
  ▼
serve_frontend.py  (:8080)
  │  静态：frontend/dist
  │  /api/* 与 SSE 流式反代
  ▼
FastAPI / uvicorn 单 worker  (:8000)
  ├── PostgreSQL 便携实例 (:5432)     任务 / 训练 / 标注元数据
  ├── NVIDIA GPU                      YOLOE / YOLO11 推理与训练
  └── 磁盘                            uploads / results / datasets / annotations / runs / 权重
```

| 端口 | 进程 | 作用 |
|------|------|------|
| **8080** | `serve_frontend.py` | 托管已构建的 SPA；把 `/api`、SSE、大文件上传**流式**反代到后端。前后端同源，前端不必写死后端 IP。 |
| **8000** | FastAPI（**必须单 worker**） | 检测、训练、历史、标注等全部业务。 |
| **5432** | 便携 PostgreSQL | 元数据持久化。不可用时检测主路径仍可跑，历史接口返回 503。 |
| **5173** | Vite（仅开发模式） | 热更新；`vite.config.js` 把 `/api` 代理到 8000。 |

覆盖端口的环境变量：`SOD_BACKEND_PORT`、`SOD_FRONTEND_PORT`、`SOD_DEV_PORT`、`SOD_PG_PORT`。开发模式后端必须保持 **8000**，否则 Vite 代理失效。

### 为什么必须单 worker

检测模型以**进程内单例**常驻 GPU（`get_detector()`）。多 uvicorn worker 会重复加载权重、占满显存。GPU 并发由 `TaskManager` 的 `asyncio.Semaphore(MAX_CONCURRENT_TASKS)` 限制，默认最多 **2** 个检测任务。横向扩展方式是「一卡一进程 + 反代」，而不是加 workers。详见第 10 节。

### Windows 启停入口

| 文件 | 作用 |
|------|------|
| `安装.bat` | 首次联网安装：便携 Node / PostgreSQL / Miniconda、CUDA PyTorch、依赖、建库、构建前端 |
| `启动.bat` | 生产模式：库 + 后端 :8000 + 前端 :8080，并打开浏览器 |
| `启动-开发模式.bat` | 库 + 后端 :8000 + Vite :5173 |
| `停止.bat` | 停前端、后端、数据库 |

Linux 离线总包则是 conda-pack 环境 + 可选 nginx / systemd，逻辑分层相同，网关换成 nginx。

## 4. 三条业务流水线

系统不是单一检测服务，而是三条可衔接的工作流。

```
AI 标注 / 人工框选 ──► 数据集 ──► YOLO11 训练 ──► best.pt 注册
                                                      │
用户自然语言 prompt ──► 开放词汇 YOLOE 检测 ◄──────────┘
                              │
                         ByteTrack + 可选 VLM 复核
                              │
                         SSE 实时帧 + ZIP 归档
```

### 4.1 流水线 A：视频开放词汇检测（主路径）

**用户路径**：上传视频 → 填中文 prompt（或选用已训练模型）→ 后台协程处理 → SSE 逐帧刷新 → 完成后下载 ZIP。

**调用链**：

1. `POST /api/upload`：流式落盘到 `uploads/{video_id}.ext`，返回元数据。
2. `POST /api/detect`：校验视频存在；可选 `prompt_normalizer` 把中文变成检测器英文短语；`task_manager.create_task`；`asyncio.create_task(run_detection_pipeline(...))`；立即 `202` 返回 `task_id`。
3. `GET /api/stream/{task_id}`：消费该任务的有界队列（SSE）。
4. 流水线在 `pipeline.run_detection_pipeline` 中获取 GPU 信号量，再 `asyncio.to_thread(_sync_pipeline, ...)`，避免堵住事件循环。

**帧循环**（`_sync_pipeline`）：

```
每一帧
  ├─ 若为检测关键帧（默认每 DETECTION_INTERVAL=5 帧，可自适应）
  │     GPU：YOLOE / Grounding DINO / Florence-2 / 已训练 YOLO11
  │     可选 SAHI 切片（大图小目标）
  │     可选颜色过滤降权
  └─ 否则
        仅把上一组检测交给 ByteTrack，Kalman 预测（纯 CPU）
        → 吞吐约 4～8×（相对逐帧 GPU）

  ByteTrack.update → 稳定 track_id
  可选：低/中置信度 track → 裁剪图送 VLM → fusion_engine 加权融合
        final ≈ 0.4 × 检测分 + 0.6 × VLM 分
        tentative → confirmed / rejected / lost
  画框、按 SAVE_FRAMES_MODE 决定是否落盘 JPEG
  FrameResult（含 base64 缩略图）入 SSE 队列

全部帧结束 → 打包 ZIP（标注帧 + results.json + results.csv）
```

**检测器选择**：

| 来源 | 何时使用 |
|------|----------|
| `get_detector()` 单例 | `.env` 的 `DETECTION_MODEL`：`yoloe`（默认）/ `grounding_dino` / `florence2` |
| `get_trained_detector(weights_path)` | 请求带已训练 `model_id`，按该权重的固定类别推理，不再开放词表 |

ByteTrack 依赖需编译的 `cython_bbox`（或 `bytetracker` 包）。未装好时日志出现 `Falling back to passthrough tracker`：**每帧新 ID、无 Kalman**，持久跟踪与间隔加速均失效。

**存帧策略**（`SAVE_FRAMES_MODE`，默认 `unique_targets`）：

| 模式 | 行为 |
|------|------|
| `all` | 每帧都存（ZIP 很大） |
| `keyframes_only` | 只存跑过检测的帧 |
| `detections_only` | 只存有框的检测帧 |
| `unique_targets` | 每个 `track_id` 首次出现存一次，之后按 `TRACK_SAVE_COOLDOWN_SEC`（默认 10s）节流 |
| `best_shot` | 每个目标整段轨迹只留质量最高的一帧（清晰度 / 面积 / 置信度 / 贴边惩罚），写盘推迟到视频结束 |

**任务控制**：`cancel` / `pause` / `resume` / `terminate`（提前结束并打包已有结果）。同步流水线用 `threading.Event` 读这些标志。

**SSE 队列**：每任务有界队列（默认 120）。客户端断开时丢最旧帧，**终态哨兵不丢**，避免 base64 帧把内存撑爆。

### 4.2 流水线 B：自定义模型训练

网页闭环：

```
建类别 (yoloe_categories)
  → 上传图 或 导入 YOLO 数据集 或 AI 标注
  → Konva 框选，YOLO txt 写在 annotations/<cat_id>/
  → POST /api/categories/{id}/train
  → dataset_builder 冻结划分（固定种子 TRAIN_SPLIT_SEED=42）
  → training_manager 拉起独立子进程 train_yoloe.py
  → 产物 runs/train/.../weights/best.pt
  → 注册 yoloe_trained_models（mAP50 过低则 needs_review，不进可选列表）
  → 检测页按 model_id 选用，无需改 .env、无需重启
```

要点：

- 训练基座是 `TRAIN_BASE_MODEL`（默认 `yolo11l.pt`），与检测用的 `YOLOE_BASE_MODEL` **刻意分开**。
- 训练不在 FastAPI 事件循环里跑。后端重启会把残留 job 标失败；Linux 上会按 `/proc/<pid>/cmdline` 确认后再收割 `train_yoloe` 进程组。Windows 上旧子进程一般随父进程一起消失。
- 默认 `imgsz=1280`、小 mosaic / 紧 scale，面向小目标；与常驻 YOLOE 共享一张卡时显存很紧，不适合检测与训练长时间并行。

类别状态大致为：`draft` → `annotating` → `ready` → `trained`。

### 4.3 流水线 C：AI 标注

配置全部在后端：`LLM_API_KEY` / `LLM_MODEL` / `LLM_API_BASE`（默认阿里云 DashScope OpenAI 兼容口，通义 VL）。密钥为空则功能提示未开通。前端不选提供商、不填密钥。

| 入口 | 行为 |
|------|------|
| `/llm-annotation` 页 + `/api/annotation-tasks` | 对已有类别批量出框，写 YOLO txt |
| `POST /api/auto-annotate` | 一站式：说目标 + 传图/视频 → 自动建带时间戳的类别并标注；视频按 sparse/medium/dense 抽帧（有总帧上限控成本） |
| 标注迭代 `/api/categories/{id}/annotation-iterations` | 多轮：pending → running → review → ready_for_training → training → trained |

出框结果进入流水线 B 的数据集，再训练、再被检测页选用，形成闭环。

图片检测（`POST /api/image-detect`）是流水线 A 的无时序版本：同一套 detector，无 ByteTrack。

## 5. 数据怎么存

### 5.1 PostgreSQL（元数据，可降级）

SQLAlchemy 2.x async + `asyncpg`。引擎 import 时创建，连接池**首次查询**才建立：DB 配错或未启动**不会阻止后端起来**。检测主路径只依赖内存 `TaskManager`；历史/训练/标注列表在 DB 失联时 503。

`init_db()` 使用 `Base.metadata.create_all`：**只建缺表，不改已有表**。Schema 演进需 Alembic。

| 表 | 用途 |
|----|------|
| `detection_tasks` | 检测任务：状态、进度、prompt、ZIP 是否就绪、错误信息 |
| `yoloe_categories` | 训练类别 |
| `yoloe_dataset_images` | 类别下每张图的路径与标注状态（pending / annotated / skipped） |
| `yoloe_training_jobs` | 训练任务进度、指标、`best.pt` 路径、子进程 PID |
| `yoloe_trained_models` | 可供检测选用的权重注册表 |
| `yoloe_annotation_iterations` | LLM 标注的用户可见迭代 |
| `yoloe_llm_annotation_tasks` | LLM 标注异步执行记录 |
| `operation_log` | 清空历史等破坏性操作审计（尚无登录，无操作者字段） |

检测任务状态：`pending` / `running` / `paused` / `packaging` / `finished` / `failed` / `cancelled` / `early_terminated`。活动中的任务不能删，须先取消。

删除任务会联动磁盘：清 `RESULTS_DIR/{task_id}/`；上传视频按引用计数，无其它任务再用才删。全量清空需 `confirm=DELETE_ALL`。

> 若干列存的是**绝对路径**（如图片 `stored_path`、训练 `dataset_yaml` / `weights_path`）。换机器且安装路径不同时，历史记录会失效，需要同路径部署或批量改路径。

### 5.2 磁盘（大文件）

| 目录 | 内容 |
|------|------|
| `uploads/` | 原视频 / 上传文件 |
| `results/<task_id>/` | 标注帧与 ZIP；图片检测在 `results/imgdet/` |
| `datasets/<cat_id>/` | 原始图与冻结后的 YOLO 数据集 |
| `annotations/<cat_id>/` | 工作中的 YOLO txt |
| `runs/train/` | Ultralytics 训练产物 |
| `backend/models/yolo/` | `yoloe-11l-seg.pt`、`yolo11l.pt` 等 |
| `backend/mobileclip_blt.ts` | YOLOE 文本编码器（开放词表**离线必需**） |
| `logs/` | `app_YYYY-MM-DD.log`，按日轮转保留 7 天 |

表只存路径，不存二进制。`.gitignore` 忽略权重与运行时数据；离线包另行打入权重。

运行期强制离线推理：`YOLO_OFFLINE=1` / `ULTRALYTICS_OFFLINE=1`，不会自动下载权重。LLM 标注走外网 DashScope，与检测离线策略独立。

## 6. API 一览

前缀均为 `/api`（健康检查除外）。错误体统一为：

```json
{ "code": "not_found", "message": "……", "detail": null, "request_id": "…" }
```

响应头带同一 `X-Request-ID`，可在 `logs/app_*.log` 里 grep。

### 健康

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/livez` | 进程存活 |
| GET | `/readyz` | DB + 模型 + GPU；未就绪 503 + 分项 |
| GET | `/health` | 浅层兼容 |

### 视频检测

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/upload` | 上传视频 |
| POST | `/api/detect` | 创建任务，202 |
| GET | `/api/task/{task_id}` | 状态（轮询备用） |
| GET | `/api/stream/{task_id}` | SSE 逐帧 |
| GET | `/api/frame/{task_id}/{filename}` | 单张标注帧 |
| GET | `/api/download/{task_id}` | 结果 ZIP |
| POST | `/api/task/{task_id}/cancel` | 取消 |
| POST | `/api/task/{task_id}/pause` | 暂停 |
| POST | `/api/task/{task_id}/resume` | 继续 |
| POST | `/api/task/{task_id}/terminate` | 提前结束并打包 |

SSE 事件类型包括 `frame` / `done` / `error` 等。`frame` 的 `FrameResult` 含 `frame_id`、时间戳、`detections[]`（`track_id`、label、score、bbox）、`image_b64`。

## 8. 一次视频检测的时序

```
前端 DetectPage
  │  FormData 上传
  ▼
POST /api/upload  ──►  uploads/{video_id}.mp4
  │
  │  JSON { video_id, prompt, detection_interval, enable_vlm, model_id? }
  ▼
POST /api/detect
  ├─ prompt_normalizer（可选）
  ├─ TaskManager.create_task  （内存 + 尽力写 DB）
  └─ create_task(run_detection_pipeline)
       立即 202 { task_id }

前端 EventSource ──► GET /api/stream/{task_id}

pipeline 持有 GPU 信号量
  _sync_pipeline 在线程池中读帧 / 推理 / 跟踪 / 融合
  每帧 push 到有界 Queue
SSE 把 frame 事件推给仍挂着的 ConsoleLayout

结束：packaging → zip_ready → event done
前端可 GET /api/download/{task_id}
```

前端 `useDetectionTasks` 把进行中的任务写入 localStorage，刷新页面后可再挂上 SSE（以后端任务状态为准）。

## 10. 设计约束（读代码时优先记住）

1. **检测主路径不依赖 PostgreSQL 和 VLM。** 历史与语义复核都是增强项；DB 挂了仍能检测。
2. **模型进程内单例 + 单 worker。** 多卡用多进程，每进程绑一张卡，前面加负载均衡。
3. **跟踪与检测解耦。** GPU 只打关键帧；身份与中间帧交给 ByteTrack。跟踪器没装好会静默降级，表现为框色乱跳、计数灌水。
4. **开放词表检测 ≠ 自定义训练。** 前者 YOLOE + MobileCLIP；后者 plain YOLO11。网页选已训练模型时走 `TrainedModelDetector`，默认关掉 VLM（仍可手动打开）。
5. **前端 layout 是状态总线。** SSE 跟页面生命周期解耦；不要把检测 hook 下放到会随路由卸载的 page。
6. **离线优先。** 权重与文本编码器必须本地存在。LLM 标注是唯一默认走公网的能力。
7. **GPU 推理在线程池，SSE 在事件循环。** 不要在流水线同步循环里直接 `await`。
8. **有界一切会涨的东西。** 上传体积、磁盘水位、SSE 队列、终态任务 LRU（`MAX_RETAINED_TASKS`）。
9. **统一可追溯错误。** 前端展示 `message`；排障用 `request_id` 搜日志。
10. **训练是子进程。** 取消/重启必须能收割，避免孤儿占 GPU。

### 横向扩展（规划，非当前实现）

- 最简：`DEVICE=cuda:0/1` 各起一个 uvicorn，Nginx upstream 负载均衡。
- 再大：用 Redis/Celery 替换进程内 `asyncio.create_task`，每卡一个 concurrency=1 的 worker。
- 吞吐旋钮：增大 `DETECTION_INTERVAL`、关 SAHI、降 `imgsz`、fp16、关 VLM。
